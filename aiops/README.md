# Agentic AIOps Platform

Multi-agent incident diagnosis on a live Kubernetes reliability platform. Deterministic triage first, a fine-tuned SLM second, a frontier model only where it earns its cost. Every proposed change is contract-validated, policy-bounded and human-gated before it touches a cluster.

This module sits inside [`axiom-mlops/axiom-platform`](https://github.com/axiom-mlops/axiom-platform), which runs Google Online Boutique under a full LGTM stack, validated to 5,000 virtual users with HPA holding. The agents diagnose incidents on that platform, not on a toy fixture.

## What is real and what is simulated

Read this before anything else. It is here on purpose.

| Component | Status |
| --- | --- |
| Underlying K8s + LGTM platform, load tested to 5K VUs | Running |
| Incident scenarios, derived from real postmortems in this repo | Real events, re-encoded as a golden set |
| Deterministic triage layer and action policy | Implemented, runnable |
| RCA contract and validation path | Implemented, runnable |
| Eval harness, scoring, cost model, report generation | Implemented, runnable, zero dependencies |
| Golden evaluation set (20 incidents) | Hand-authored, synthetic |
| Model outputs in `evals/fixtures/` | Replay fixtures. A stated target envelope, not measurements |
| Fine-tuned Qwen3.5-9B served on vLLM | Configured, not yet trained or served in this snapshot |
| EKS deployment (Terraform / Helm) | Scaffolded, partial |

Nothing in `evals/results/` is typed by hand. It is generated by the harness from the golden set plus the engine output. Point the harness at a served model with `--engine vllm` and the same report regenerates with real measurements. That swap is the only thing standing between this snapshot and live numbers, and it is deliberately the only thing.

## The architecture, and the one idea behind it

```
  alert / telemetry event
          |
          v
  +-------------------+   matched   +------------------------+
  |  1. TRIAGE        |------------>|  deterministic outcome |
  |  rules, DB lookup |             |  0 tokens, 38 ms       |
  +-------------------+             +------------------------+
          | unmatched
          v
  +-------------------+
  |  2. ROUTER        |  anonymize, then decide who answers
  |  frontier model   |  routine class -> local SLM
  +-------------------+  novel or cross-scope -> frontier
          |
          v
  +-------------------+     +----------------------------+
  |  3. RETRIEVE      |<--->| Qdrant, BGE-M3 + reranker  |
  |  context slicing  |     | runbooks, prior incidents  |
  +-------------------+     +----------------------------+
          |
          v
  +-------------------+
  |  4. DIAGNOSE      |  Qwen3.5-9B, QLoRA, vLLM
  |  constrained JSON |  emits against rca.schema.json
  +-------------------+
          |
          v
  +-------------------+   fails   +-------------------------+
  |  5. GUARDRAIL     |---------->| blocked, never reaches  |
  |  schema + policy  |           | a human approver        |
  +-------------------+           +-------------------------+
          | passes
          v
  +-------------------+
  |  6. HUMAN GATE    |  PagerDuty approval, rollback attached
  +-------------------+
          |
          v
    execute -> verify -> write runbook -> emit metrics to Grafana
```

The idea worth defending: **most of the work in an AIOps system is deciding what not to send to a model.** Six of the twenty golden incidents are resolved by rules, at zero tokens and 38 milliseconds. Of the fourteen that remain, the local SLM handles all of them at roughly 1/160th of frontier token cost and a quarter of the p90 latency, giving up 7.2 points of top-1 accuracy. The frontier model is kept for routing and for novel classes, where its generalization is worth paying for.

An AIOps platform that sends every alert to a large model is not an AI platform. It is an expensive alert forwarder.

## Results

Full report with methodology: [`evals/results/RESULTS.md`](evals/results/RESULTS.md)

| Metric | Fine-tuned SLM (local) | Frontier baseline |
| --- | --- | --- |
| Root cause top-1, model-routed incidents | 85.7% | 92.9% |
| Proposed action inside guardrail policy | 100.0% | 100.0% |
| RCA parsed against contract first try | 100.0% | 95.0% |
| Latency p90 | 932 ms | 3,760 ms |
| Context slicing token reduction | 40.0% | not applicable |
| Inference cost per incident | $0.00007 | $0.01117 |

Two rows deserve a comment.

**Schema validity is inverted, and it matters more than accuracy.** Constrained decoding on the local server gives first-try contract compliance. The frontier baseline occasionally wraps valid JSON in prose. In a pipeline, an unparseable RCA is not a quality regression, it is a failed automation run that pages someone.

**Action policy pass rate is the safety number.** Both engines proposed only actions inside the cause-scoped allow list. This is what bounds the damage of a wrong diagnosis: the worst case is a rejected suggestion, not a bad change.

## Roadmap

The chassis is shared. Each agent is the same detect, reason, propose, gate, execute, verify loop pointed at a different part of the incident lifecycle.

1. **Triage and RCA agent** (this module) - respond faster
2. **Deployment verification agent** - canary analysis, chaos and load in staging, prevent the incident
3. **Right-sizing agent** - continuous resource optimization against real utilization

Next steps in order: train the QLoRA adapter on the incident corpus, serve on vLLM, rerun the harness with `--engine vllm`, publish measured numbers alongside the replay numbers so the gap between target and reality is visible rather than hidden.

# Earlier module notes


The reasoning code lives in [axiom-aiops](https://github.com/axiom-mlops/axiom-aiops).
This directory is the seam where it meets the cluster: the alert that triggers it,
the route that delivers it, and the identity that bounds what it can touch.

| Path | What it does |
|---|---|
| `alerts/saturation-rules.yaml` | Defines `ContainerMemoryNearLimit` — the alert the agent's demo diagnoses — plus a rule that detects the HPA blind spot directly |
| `alerting/alertmanager-agent-route.yaml` | Routes `aiops_eligible` alerts to the agent webhook while the human page fires unchanged |
| `rbac/agent-serviceaccount.yaml` | ServiceAccount, Role, RoleBinding scoping the executor to HPA patches and scale subresources |

## The design property these three files enforce

The agent's safety story has two halves, and only one of them is in the agent's code.

In [axiom-aiops](https://github.com/axiom-mlops/axiom-aiops), the model selects from a
typed whitelist of actions and a human gate stands between proposal and execution.
That is application-level control — necessary, but it is code, and code has bugs.

These files are the half that does not depend on the agent behaving correctly. The
Role grants patch on HorizontalPodAutoscalers and nothing else, so a compromised,
confused, or prompt-injected agent still cannot delete a Deployment, read a Secret,
or exec into a pod. The API server refuses, and no amount of clever input changes that.

Defence in depth: the whitelist is what the agent *will* do; RBAC is what it *can* do.

## Apply

```bash
kubectl apply -f aiops/rbac/agent-serviceaccount.yaml
kubectl apply -f aiops/alerts/saturation-rules.yaml
kubectl apply -f aiops/alerting/alertmanager-agent-route.yaml

# Confirm the permission boundary is real
kubectl auth can-i patch hpa --as=system:serviceaccount:boutique:aiops-rca-agent -n boutique   # yes
kubectl auth can-i delete deployment --as=system:serviceaccount:boutique:aiops-rca-agent -n boutique  # no
kubectl auth can-i get secrets --as=system:serviceaccount:boutique:aiops-rca-agent -n boutique       # no
```

Those three `can-i` checks are worth running on camera. They turn "least privilege"
from an assertion into a demonstration.
